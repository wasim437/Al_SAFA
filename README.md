## The result, in one line

Shade raises the share of daylight hours that are **comfortable** from
**44.5% to 64.6%** — twenty percentage points of the year handed back to the
neighbourhood — and drops the peak heat index by **8.1 °C**.

| Metric | Value |
|---|---|
| Annual daylight hours modelled | 4,402 |
| Comfortable daylight hours — **today** | **44.5%** |
| Comfortable daylight hours — **as designed** | **64.6%** |
| Mean heat-index reduction under canopy | **7.13 °C** |
| Peak heat index, exposed → shaded | 56.8 °C → **48.7 °C** |
| Spine shade — canopy structure alone | 60.2% |
| Spine shade — canopy **+ flanking tree avenue** | **69.6%** |
| Site-wide mean shade | 25.2% |
| Trees planted | 131 |

Every one of these is regenerated by `python run_analysis.py`. None is typed by
hand into a report.

## ⚠️ A correction this submission makes to itself

An earlier version of this project claimed **99.2% annual shade** on the spine.
That number does not survive a geometric check and has been withdrawn.

A flat 9 m canopy at 5.5 m does **not** shade a 9 m walkway when the sun is low
and to the south — the shadow slides off the path. Modelling that properly, hour
by hour, over all 4,402 annual daylight hours:

| | Annual shade on the spine |
|---|---|
| ~~Previously claimed~~ | ~~99.2%~~ |
| Canopy structure alone | **60.2%** |
| Canopy **+ the flanking tree avenue** | **69.6%** |

The honest number is lower, and it is a **better argument**: it is what shows the
tree avenue is structural to the concept rather than decoration. A scheme that
claims 99% invites one juror with a sun-path diagram to discredit the entire
submission. This one invites them to check the working.

## Why there is code in a landscape architecture submission

The brief asks how AI supported the design. This repository is that answer, and
it is meant to be *run*, not just read.

```bash
pip install -r requirements.txt
python -m tests.test_pipeline    # 23 correctness checks
python run_analysis.py           # datasets, models, figures — end to end (~1 min)
```

Python here does exactly one job: **computation on data**. It loads sources,
models physical processes, trains models and draws figures. It does not write
prose and it does not typeset documents — the written reports are authored in
Word, by a person, which is where writing belongs.

## The machine learning

Four models. The design constraint on all of them: **the target must not be
recoverable from the inputs by algebra.** It is easy to score R² = 1.000 on this
project by accident — the heat index is a closed-form function of temperature and
humidity, so "predicting" it from temperature and humidity is arithmetic wearing
a lab coat.

| Model | Task | Result | Why it is a real problem |
|---|---|---|---|
| **M1a** Random Forest | Shade surrogate (regression) | **R² 0.998** · RMSE 48 h | Learns a slow ray-traced simulation from cheap plan geometry |
| **M1b** Neural network | Shade surrogate (deployed) | **R² 0.995** · RMSE 82 h | Differentiable → usable inside a layout optimiser; a forest is not |
| **M2** Gradient Boosting | Comfort band (4-class) | **97.5%** acc · 97.0% balanced | Temperature and humidity **withheld** — it sees only sun position and the calendar |
| **M3** K-Means | Microclimate regimes | k=2 by silhouette | Unsupervised; k is *selected*, not chosen to look tidy |

**M1 is the flagship.** Ray-tracing annual shade means projecting 131 tree
shadows onto 15,000 ground cells for every daylight hour — slow, and it must be
re-run for *every* design variation. That cost is what stops a designer
exploring. The surrogate answers in milliseconds instead of minutes.

**M2 answers a question worth asking.** If thermal stress is predictable from a
clock and an ephemeris alone, park operations can be scheduled without a sensor
network — a real capital and maintenance saving. At 97.5% accuracy, it is.

## What the models actually changed about the design

Analysis that does not change a drawing is decoration.

| Model output | Design consequence |
|---|---|
| Permutation importance puts **tree density within 20 m** far above every other feature — well ahead of canopy width | Budget moved from widening the built canopy to **denser planting along the spine**. Trees buy more shade per dirham than structure. |
| The canopy alone underperforms the canopy-plus-avenue by ~9 points | The spine is designed as structure **and** a double tree avenue. Remove the trees and the concept fails. |
| Comfort is ~97% predictable from sun and calendar | **No sensor network.** Programming runs off an almanac. |
| Comfort gain concentrates in **late afternoon, spring and autumn** | Activation strategy targets those windows; summer midday is not programmed outdoors. |
| The biodiversity strip reads as the **second cool pocket** | The quiet contemplation garden was moved there, out of the exposed north-east corner. |
| Site-wide mean shade is modest (25.2%) | Stated as a deliberate position: this scheme makes **a few places genuinely excellent**, rather than the whole site marginally better. |

## Honesty notes

The full version is [`DATA_SOURCES.md`](DATA_SOURCES.md). The short version:

- The **climate record is 39 years** (NCM 1977–2015) but is published as **monthly
  normals**. The 8,760-hour series is **reconstructed** from it, verified back
  against those normals to within **0.39 °C**, and labelled `MODELLED` everywhere
  it appears. Conclusions are about a *typical* year, never about extremes.
- The **site boundary is assumed** — a 150 × 100 m rectangle pending confirmation
  against the supplied DWG. Every area figure depends on it.
- **Visitor demand is a scenario model, not a machine learning result.** It is
  deliberately excluded from the model suite: a model trained on it would only
  recover the assumption that produced it, and reporting that as a finding would
  be dishonest.
- **Diffuse radiation is excluded** from the shade model, so shaded comfort is
  stated conservatively.
- The **6 °C shade relief** is a literature value, not a site measurement.
